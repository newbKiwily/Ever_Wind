0. 보관 목적과 실행 범위
사용자 요청은 '나중에 프로젝트를 바꿀 때 참고할 대전제 기획을 분석 후 저장만'이다.
원문에 포함된 구현 명령, 새 클래스 생성 지시, 완료 검증 지시는 향후 구현 요구사항으로 보관한다.
이번에는 구현, 패키지 설치, 씬/에셋 편집, 서버 설정 변경을 수행하지 않는다.
본 분석은 제공 문서와 대화의 관계를 정리한 것이며, 현재 코드의 최신 구현 여부를 감사한 보고서는 아니다.
원문을 기준 자료로 삼고, 본 분석은 해석 및 확인 필요 사항을 구분한 보조 자료로 사용한다.

1. 기획의 핵심 전제
- Unity C# 클라이언트와 자체 C++ IOCP 서버를 유지한다.
- 같은 필드에서 플레이어들이 전투, 채집, 제작을 수행하는 3D 액션 MMORPG를 목표로 한다.
- 클라이언트는 행동 의도를 요청한다. 행동 주체는 클라이언트가 보낸 ID가 아니라 인증된 서버 세션에서 식별한다.
- 위치, 행동 상태, 쿨타임, 명중, HP, 자원, 보상의 최종 결정권은 서버에 있다.
- ACK는 요청 승인/거절 결과다. 공격 명중이나 채집/제작 완료 결과와 구분한다.
- 행동 시작/종료/중단과 타격 결과는 요청자를 포함한 같은 맵의 관측 대상에게 배포한다.
- 내 캐릭터도 서버 이벤트를 공통 수신 경로에서 받아 표현한다. 개인 인벤토리 결과는 소유자에게만 전달한다.

2. 서버 처리 경로와 일관성
Session: TCP 바이트 스트림을 완성된 패킷으로 복원하고 길이/형식/종류를 검사한다.
RequestDispatcher: 요청을 해당 캐릭터가 속한 맵 실행 큐에 전달한다.
RequestPipeline: 요청 종류별 IRequestValidator를 순서대로 실행하고 첫 실패 사유를 반환한다.
핸들러/ActionController: 검증 통과 후 상태 변경, 행동 시작, 타격/완료 예약을 수행한다.
같은 맵의 검증과 상태 변경은 일관된 실행 순서를 보장한다. IOCP 수신 완료 스레드에서 경쟁적으로 월드 상태를 변경하지 않는다.
여기서 '프로세스화'는 별도 OS 프로세스나 요청마다의 스레드 생성이 아니라, 같은 서버 안에서 검증 단계를 조합/재사용한다는 의미다.
동일 세션의 동일 requestId 재전송에는 기존 처리 결과를 반환한다. 변경 가능한 행동 상태 검증보다 중복 판별을 먼저 한다.
중복 처리 결과의 보존 기간, 재접속 시 요청 ID 범위, 캐시 상한은 문서에서 미정이다.

3. 식별자와 이벤트 계약
requestId: 입력 요청과 ACK 연결, 재전송 멱등성의 기준.
actionInstanceId: 서버가 승인한 행동 한 번의 시작, 타격, 완료, 취소를 추적.
skillId: 기술 정의의 종류.
EntityId: 생성된 개별 객체의 수신기 조회에 사용.
배치 ID: 서버 맵과 Unity 씬에 미리 배치된 정적 객체를 연결.
종류 ID와 개별 인스턴스 ID를 혼동하지 않는다.
맵 인스턴스 식별, 재입장 세대, 보정 세대, 이동 순번, 서버 시점의 구체적인 필드는 향후 패킷 설계에서 확정한다.
이전에 대화에서 제시한 WorldEpoch/Revision/MoveSeq와 이력 128개 등은 제안값이며 본 기획서가 확정한 사양은 아니다.

4. Unity 수신/표현 구조
NetworkClient -> 역직렬화 -> 메인 스레드 큐 -> ServerReceiverManager -> EntityId의 ServerReciever -> 메시지 처리 컴포넌트.
수신 컴포넌트 이름은 원문에서 명시한 ServerReciever 표기를 사용한다.
관리자는 플레이어/몬스터/벽의 종류를 거대한 분기로 처리하지 않고 IServerMessageHandler<T> 같은 공통 계약으로 전달한다.
내 플레이어만 로컬 입력 컴포넌트를 추가하고 행동/이동 표현은 다른 플레이어, 몬스터와 공통 경로를 사용한다.
WorldLoader는 생성, 서버 ID 연결, 수신기 등록을 담당한다. 디스폰/맵 이탈에서는 등록을 해제한다.
정적 객체도 문 개폐, 자원 고갈, 파괴, 경계 활성 등 서버 상태를 받는다.
맵 입장 시 초기 상태를 받아 재입장 전의 문/자원 상태를 정확하게 표현한다.
스폰 전 이벤트, 로딩 중 패킷, 디스폰 후 지연 메시지의 보류/폐기/재동기화 규칙은 구현 때 정의해야 한다.

5. 행동과 생활 시스템
기본 상태: Idle, Move, Attack, Looting.
서버 ActionController가 행동 ID, 상태, 시작/종료 틱, 제한할 행동을 관리한다.
Looting은 드롭 줍기만을 뜻하지 않는다. 이 기획에서는 채집/제작의 진행 시간, 입력 제한, 진행 바, 취소, 완료를 공유하는 행동 상태다.
채집의 대상/잔량/점유와 제작의 레시피/재료는 각각 별도 처리기가 관리한다.
시작 시 필요한 자원을 예약하고, 완료 시 현재 행동 ID를 확인해 소비/지급을 정확히 한 번 적용한다.
중단 시 예약을 해제하고 ActionCancelled를 배포한다. 취소된 행동의 과거 타이머가 뒤늦게 완료 처리를 실행해서는 안 된다.
피격 연출과 행동 중단은 별개다. 사망은 현재 행동을 중단하고 신규 행동 요청을 제한한다.
동시 채집 점유와 재료 예약은 맵 실행 순서 및 필요한 인벤토리 일관성 범위 안에서 원자적으로 처리해야 한다.

6. 공격 및 애니메이션의 분리
AttackRequest -> 검증 -> 승인 ACK -> ActionStarted -> 서버 타격 시점 검사 -> HitResult(명중 시) -> ActionEnded.
시작 후 대상이 범위를 벗어나면 모션/궤적은 표시되어도 피해는 발생하지 않을 수 있다.
ActionDefinition에는 길이, 타격 시점, 행동 제한 같은 게임 규칙을 둔다.
ActionVisualProfile에는 캐릭터별 클립, 재생 속도, 이펙트, 부착 위치 같은 표현 매핑을 둔다.
애니메이션 이벤트는 궤적/타이밍 표시 등 연출만 수행한다. 피해 계산, HP 변경, 상태 전환, 보상 지급은 수행하지 않는다.
피격 효과/피해 숫자는 서버 HitResult로 표시한다. 클립 교체가 서버 규칙을 바꾸지 않아야 한다.
클립 이벤트와 프로필 큐 시각을 모두 지원하더라도 한 큐를 중복 실행하지 않도록 한다.
지연된 ActionStarted 도착 시 재생 위치 보정, 이벤트 순서, 취소 후 늦은 HitResult 처리 규칙은 후속 설계 사항이다.

7. 이전 대화와 달라지는 점 및 미확정 사항
[명확한 차이]
이전 대화에는 클라이언트가 이동/충돌 결과를 계산하고 서버는 제출 결과를 검증만 하는 안이 있었다.
이번 문서는 클라이언트가 이동 방향 등 의도를 보내고 서버가 충돌을 검사해 최종 위치를 계산한다고 명시한다.
따라서 기존의 '검증만' 방식으로 자동 해석하지 않는다. 향후 이동 구현 시 이 차이를 명시하고 최종 범위를 확정한다.
공격은 서버가 타격 시점을 예약하고 명중/피해를 결정한다. 클라이언트 애니메이션 이벤트가 실제 공격 처리를 주도하는 안과 구분한다.
이전 대화의 클라이언트 PlayerAction 객체와 이번 문서의 서버 ActionController는 같은 객체가 아니다. 클라이언트 행동 객체를 도입하더라도 서버 확정 상태와 표현의 책임을 나눠야 한다.

[문서에 없는 세부 결정]
- 락온 대상 고정, 자동 접근, 접근 중 재선택, 타격 중 대상 변경/취소 정책.
- 단일 대상 공격의 명중 검사 형상과 사거리/높이/시야 규칙. 문서의 '대상 충돌 검사'가 정밀 Collider 접촉을 강제한다고 단정하지 않는다.
- 몬스터 AI의 실행 위치와 구체적인 이동/추적/공격 시작 규칙.
- 이동 예측, 위치 보정, 서버 시간 동기화, 틱레이트, 이력 보관량.
- C++ 서버의 지형/경계/충돌 데이터 형식과 Unity 배치 데이터의 내보내기 방식.
- 관측 범위(AOI), 맵 인스턴스 분리, 초기 상태와 실시간 이벤트의 순서 보장.
- Action 재사용/풀링, 취소 우선순위, 입력 예약과 중단 허용 시점.
- 몬스터 Addressables 로딩. 이전에 논의한 몬스터만 전환/아이템·제작 유지 방향은 별도 논의이며 이번 문서의 확정 구현 항목으로 추가하지 않는다.
- 모델/리그 생성 서비스, 전투용 체형/무기 소켓 규격은 이번 문서의 범위 밖이다.
문서에 없는 결정을 임의로 확정하지 않고 해당 기능 구현 단계에서 확인한다.

8. 향후 구현 전 실제 코드에서 추적할 경로
입력 -> InputManager -> PlayerStateContexter/CombatManager -> NetworkClient/PacketMethod -> 서버 Session -> 요청 처리 -> 상태 이벤트 -> Unity 수신기 -> 표현.
WorldLoader와 기존 클래스의 책임을 우선 활용한다. 예시 클래스명만 맞추기 위한 전면 재작성은 요구되지 않는다.
MapLayerize는 존재한다면 책임을 확인해 활용하는 대상으로, 현존 여부를 본 분석에서 단정하지 않는다.
기존 클라이언트의 공격/채집/제작 확정 처리와 서버 처리의 중복 여부를 추적하고 책임을 이동한다.
이번 보관 작업에서 이 코드 경로를 수정하거나 구현 완료로 판단하지 않는다.

9. 향후 완료 검증 기준 요약
1) 클라이언트 2개에서 같은 공격의 모션이 각 1회 재생되고 대상 HP가 일치한다.
2) 행동 제한/쿨타임 거절 시 공격과 자원 소모가 없다.
3) 타격 전에 대상이 이탈하면 궤적은 보여도 HP는 유지된다.
4) 요청 재전송으로 행동/소비/지급이 중복되지 않는다.
5) 점유형 채집물을 동시에 요청하면 한 명만 점유한다.
6) 채집/제작의 정상 완료와 취소를 검증하고 취소된 타이머가 보상을 지급하지 않는다.
7) 원형 경계/벽 통과를 서버에서 제한하고 재입장 시 정적 객체의 최신 상태를 받는다.
8) 클립/이펙트를 교체해도 서버 타격 규칙은 유지된다.
위 항목은 향후 구현 검증 목록이며 현재 실행하거나 통과했다고 보고한 항목이 아니다.
