2026-11-12

현재 게임플레이 요청 흐름
Session/IOCPServer 수신 및 TCP 패킷 조립
 -> RequestDecoder: 패킷 검증부에 프레임·인증 확인 요청 후 Request 구조체 복원
 -> Service: 인증된 연결 ID 및 요청을 게임 작업 큐로 전달
 -> Core: 요청 계약 검사, 중복 요청 처리, 플레이어/맵 문맥 구성
 -> GameplayValidation: 공통 검증 체인 및 요청별 체인
 -> GameplayProcessor: 검증된 요청 실행, 서버 상태 변경 및 결과 이벤트 생성
 -> GameplaySender: Event 직렬화, 연결 생존 확인
 -> Session::PostSend / WSASend

책임별 클래스
- Core: 요청 파이프라인 조정, 중복 요청 캐시, ACK 기록/반환. 기존 약 1,300줄에서 113줄로 축소했다.
- WorldState: 플레이어/몬스터/맵/아이템/레시피/퀘스트 상태, 규칙 파일·지형 자료 로딩, 대상 조회 및 공통 거리 판단.
- PacketValidation: 구체 클래스 PacketValidator 한 개를 보관하며 파싱 전 프레임·인증과 파싱 후 요청 계약 검사를 호출.
- GameplayValidation: 공통 체인 및 RequestKind별 체인 보관·실행·중간 삽입.
- GameplayProcessor: 이동 반영/거부 보정, 공격/채집/제작/아이템/퀘스트/튜토리얼/저장 처리와 시간에 따른 행동·몬스터 갱신.
- RequestDecoder: 검증된 바이트 본문을 Request로 해석.
- GameplaySender: 이벤트를 0x501 패킷으로 직렬화하여 Session 송신 큐로 전달.
- Service: 기존 단일 게임 작업 스레드와 요청 큐 유지. 새로운 OS 프로세스나 병렬 워커는 도입하지 않았다.

Validator 상속과 소유권
Validator (공통 next/검사 실행/삽입)
 -> PacketValidator (구체 클래스, 패킷 기본 검사 직접 수행)

IngameValidator

 -> SkillExistsValidator / CombatModeValidator / AttackTargetValidator / AttackRangeValidator / AttackCooldownValidator
 -> NonCombatModeValidator / ResourceExistsValidator / GatherRangeValidator / ResourceAvailabilityValidator
 -> RecipeExistsValidator / CraftIngredientsValidator / CancelActionValidator / MapExistsValidator

 -> TutorialMovementValidator / TutorialAttackValidator / TutorialMapValidator / TutorialProgressValidator

- 각 구체 Validator는 자기 이름의 헤더·CPP를 가진다. 패킷 구조체는 기존 공용 헤더를 유지한다.
- 기본 클래스가 unique_ptr next를 소유한다. Check가 자신의 Validate 결과를 확인하고 성공한 경우에만 next->Check를 호출한다.
- 검사별 클래스는 람다 등록용 껍데기가 아니다. 검사 본문이 각 Validator CPP에 들어 있다.
- ActionIdleValidator 등 같은 조건의 클래스는 여러 요청 체인에서 재사용하되, 연결 노드 인스턴스는 각 체인이 독립 소유한다.
- 체인은 생성자에서 Initialize를 호출해 한 번 조립한다. 요청마다 노드를 생성하거나 순서를 다시 구성하지 않는다.
- 이전 IRequestValidator/LambdaValidator/ValidationGroup 파일과 등록 코드는 제거했다.

조립 예: GameplayValidation::Initialize
common = make_unique<WorldEpochValidator>(world);
common->Then(make_unique<AliveRequestValidator>(world))
      .Then(make_unique<ForcedMovementValidator>(world));

중간 삽입
GameplayValidation::InsertBefore(kind, 기존 노드 이름, 추가할 unique_ptr<IngameValidator>)를 사용한다.
삽입할 노드의 next에 기존 노드를 연결하므로 나머지 체인이 유지된다. 헤드 앞 삽입도 같은 방식으로 처리한다.
대상 이름이 없으면 false를 반환하고 기존 체인은 바꾸지 않는다. 이미 연결된 Then 호출은 기존 next를 덮어쓰지 않고 logic_error 예외를 발생시킨다.
검사 순서에는 의존성이 있다. 예를 들어 대상 존재/스킬 존재 검사는 해당 대상/스킬을 사용하는 사거리 검사보다 먼저 두어야 한다.
체인 변경은 초기화 또는 동일 게임 작업 스레드에서만 수행한다. 다른 스레드에서 실행 중인 체인을 동시에 수정하는 용도로 제공한 API가 아니다.

범위와 유지한 동작
- 패킷 번호, Request/Event 필드, 52/108바이트 본문 크기, 클라이언트 프로토콜은 유지했다.
- 기존 로그인/회원가입 처리와 DB 스키마는 유지했다. 새 경로는 0x500 게임플레이 요청의 수신 어댑터와 Core 처리에 적용했다.
- 동일 작업 스레드 안에서 검증 후 처리를 연속 실행하므로 검사 직후 다른 워커가 같은 상태를 변경하는 구간을 추가하지 않았다.
- 공격 타격 시점과 채집/제작 완료 시점의 재확인은 처리부의 기존 실행 안전 검사로 유지했다. 시작 요청의 쿨타임/Busy 검사를 완료 시점에 그대로 재실행하지 않는다.
- 월드 상태는 Core, 검증부, 처리부 사이에서 복사하지 않고 같은 WorldState를 참조한다. 기존 스마트 포인터 소유권과 송신 weak_ptr를 유지했다.

후속 변경: 패킷 기본 검사 세 클래스를 BasicPacketValidator 하나로 통합했다. PacketValidator 상속과 next 확장 기능은 유지하며, 본문 복사 전 크기·인증 확인과 복사 후 버전·요청 종류 확인 순서를 보존한다. PacketContext의 검사 단계는 서버 내부 정보이며 전송 패킷에는 추가하지 않았다.

최신 상속 정리: 공통 Validator가 next, Check, Then, InsertBefore와 소유권을 담당한다. PacketValidator는 Validator를 상속하는 구체 클래스이며 BasicPacketValidator는 제거했다. IngameValidator는 Validator를 상속하는 추상 클래스로 기능별 게임 검증의 기반이다. 패킷 문맥과 게임 문맥은 Check/Validate 오버로드로 구분하고, 문맥이 맞지 않는 노드는 BadRequest로 중단한다. 직접 생성 가능 여부와 공통 부모를 통한 체인 실행도 회귀 검사에 추가했다.
