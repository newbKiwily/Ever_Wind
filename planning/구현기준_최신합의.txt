EverWind 구현 기준 — 최신 대화 합의
갱신일: 2026-11-12 (Asia/Seoul)

적용 관계
이 파일은 MMORPG_Codex_구현요청서.txt 원문을 대체/편집하지 않고, 이후 사용자가 명시적으로 수정하거나 확정한 내용을 기록한다.
향후 구현에서 원문과 충돌하는 항목은 아래 최신 합의를 적용한다.
이 파일 저장은 구현 완료를 뜻하지 않는다. 최신 지시에 따라 합의한 작업 범위까지 자율적으로 진행하고 완료 시 변경 코드와 검증 결과를 보고한다.

1. 플레이어 이동
- 클라이언트가 이동 후보 위치를 계산하고 예측 이동한다.
- 서버는 인증된 세션을 기준으로 이동 주체를 식별한다.
- 서버는 클라이언트가 보고한 충돌이 있을 때만 검사하는 것이 아니라 모든 이동 요청의 이동 구간을 검사한다.
- 서버는 책임 연쇄 방식의 재사용 가능한 검증 단계를 적용해 이동을 승인/거부한다.
- 승인 시 서버 확정 위치를 갱신하고, 거부 시 확정 위치와 요청 식별 정보를 보내 클라이언트가 보정한다.
- 이는 TXT의 '이동 방향 등 의도를 받아 서버가 플레이어 이동을 직접 계산'하는 설명에 대한 명시적인 변경이다.
- 경계, 장애물, 캐릭터 크기는 서버도 알고 있어야 하며, 도착점만이 아니라 마지막 확정 위치부터 요청 위치까지 검사한다.
- 입력/이동 순번, 맵 세대, 보정 세대, 서버 기록 시간 등의 실제 패킷 형식은 구현 전 계약 단계에서 정한다.

2. 몬스터 권한과 이동
- 몬스터 정의, 생성된 몬스터 상태, HP, 이동 및 행동 결정권은 서버가 전담한다.
- 서버 코드에서 배회/이동 등 필요한 연산을 수행한다. 클라이언트에 몬스터 AI나 이동 권한을 위임하지 않는다.
- 클라이언트는 서버에서 받은 몬스터 위치와 행동 정보를 보간/표현한다. 클라이언트 표현의 갱신은 게임플레이 상태의 결정권을 의미하지 않는다.
- Unity 수신기는 서버 결과를 몬스터의 이동/행동 표현 컴포넌트에 전달한다.
- 서버 내부 몬스터 이동도 서버 맵의 충돌/경계 규칙을 지켜야 한다. 구현 시 필요한 검증 기능을 공유하되 클라이언트발 몬스터 이동 요청 경로는 사용하지 않는다.

3. 공격, 채집, 제작
- TXT의 서버 권위를 유지한다. 서버가 공격 타격 시점, 명중, 피해, HP, 자원 소비 및 보상을 확정한다.
- ACK는 요청 승인/거절이며 명중이나 완료를 의미하지 않는다.
- 클라이언트는 요청과 행동 표현을 담당한다. 애니메이션 이벤트는 피해/상태 전환/보상을 확정하지 않는다.
- 요청 멱등성, 서버 행동 인스턴스 ID, 시작/타격/종료/취소 이벤트, 예약/점유 해제 규칙을 유지한다.

3-1. 서버 책임 연쇄 검증 그룹과 기존 코드 재사용
- 사용자 확정: 검증을 공통 검증 그룹과 요청/행동별 구체화 검증 그룹으로 나누고 기존 자료구조 및 검사 코드를 최대한 재사용한다.
- Session의 TCP 복원/길이/형식/패킷 종류 검사는 진입 계층에서 유지하고, 맵 상태를 사용하는 검사 및 변경은 맵 실행 큐에서 순서대로 처리한다.
- 인증된 세션/주체/요청 범위 확인 후 중복 요청을 먼저 확인한다. 같은 요청은 기존 결과 반환 또는 진행 중 요청 병합으로 처리하고, 변경 가능한 생존/행동/쿨타임 검사와 실행을 다시 수행하지 않는다. 동일 ID에 다른 내용인 요청은 충돌로 거절한다.
- 공통 그룹은 요청에 필요한 주체/맵/행동 허용 규칙 등을 재사용 가능한 검증 단계로 구성한다. 모든 요청에 무조건 생존 또는 동일 행동 제한을 강제하지 않는다. 부활/취소 등은 해당 요청의 정책을 적용한다.
- 구체화 그룹: 이동(순번/세대/유효 수치/허용 이동거리/이동 구간 충돌/경계), 공격(스킬/대상/자원/쿨타임/시작 조건), 채집(대상/거리/도구/잔량/점유), 제작(레시피/재료/작업대 조건), 취소(현재 행동 ID/취소 허용 여부).
- 같은 거리/대상/자원 등의 검사 기능은 여러 구체화 그룹에서 조합해 사용한다. 그룹 분리는 큰 상속 트리보다 공통 인터페이스를 통한 체인 조합을 우선한다.
- 검사 단계는 통과 또는 실패 사유를 반환하며 처음 실패하면 실행을 중단한다. ACK 전송은 파이프라인의 공통 처리에서 담당해 검사마다 중복 응답하지 않는다.
- 기존 PacketMethod/Session/MapData/Enemy 및 인벤토리/레시피 접근을 활용하되, 검증과 갱신/전송/DB 쓰기가 섞인 함수를 검증기에서 그대로 호출하지 않는다. 검사 부분과 실행 부분을 필요한 범위에서 분리한다.
- 자원 예약/쿨타임 시작/재료 소비/보상/상태 변경은 전체 검증 통과 후 실행 단계에서 수행한다. 검사만으로 일부 상태가 먼저 변경되지 않게 한다.
- 서버 내부 몬스터 이동에는 공통 충돌/경계 검증을 재사용하되 클라이언트 세션/요청 중복 검사까지 억지로 적용하지 않는다.
- 타격/채집 완료 시점의 재검증과 시작 요청 검증을 구분한다. 이미 시작한 행동을 초기 쿨타임 검사로 다시 거절하지 않고, 해당 행동 ID와 완료/타격 조건을 검사한다.

4. 클라이언트 State와 Action
- State는 NonCombat/Combat/Looting/Dead를 기본 모드로 하여 Action 허용, 거절 및 표현 기준을 제공한다.
- 기존 TXT의 Idle/Move/Attack/Looting 상태 구분을 그대로 구현하지 않는다. Idle/Move/Attack 등은 Action 역할로 분리한다.
- ActionController가 실행, 교체, 취소, 예약 및 인터럽트 정책을 통합 관리한다.
- MoveAction은 속도/방향, 이동 검사, 이동 실행 및 예측/요청 연결의 공통 기반이다.
- ApproachTargetAction과 KnockbackAction은 MoveAction을 상속한다.
- AttackAction은 MoveAction 또는 ApproachTargetAction을 알지 않는다. 사거리 안이면 공격을 요청하고 밖이면 실패 결과를 반환한다.
- Controller가 대상과 목적을 보관하고 접근 정상 완료 후 공격/채집/대화 등의 후속 행동을 시도한다.
- 대상 선택 변경과 진행 중인 작업의 대상 변경은 분리한다.
- 접근/직접 이동/넉백이 동시에 위치 제어권을 갖지 않도록 한다.
- 작업 ID/실행 세대로 지연 콜백을 구분하고 정상 도착, 취소, 대상 소멸, 막힘, 시간 초과를 구분한다.
- 일반 피격 표현과 행동 중단을 분리한다. 서버가 확정한 피해 결과는 로컬 작업이 취소되었다는 이유만으로 폐기하지 않는다.
- 재사용 가능한 Action은 캐릭터별로 재사용하되 실행 상태/구독/타이머를 초기화한다. 상태를 가진 실행 객체를 캐릭터 간 전역 공유하지 않는다.

5. 엔티티 송수신 명칭과 책임
- 사용자는 TXT의 ServerReciever 및 이후 ServerReceiver 명칭을 수정하여, 오브젝트별 컴포넌트가 송신과 수신을 모두 담당함을 명시했다.
- 엔티티 송수신기는 ServerTransceiver, 등록/조회 관리자는 ServerTransceiverManager로 명명한다.
- Transceiver는 송신기(Transmitter)와 수신기(Receiver)를 합친 송수신기를 의미한다.
- ServerTransceiver는 해당 오브젝트의 EntityId와 수명을 연결하고, 허용된 행동 요청을 NetworkClient에 전달하며, 서버 메시지를 공통 처리 컴포넌트에 분배한다.
- 수신: NetworkClient -> 역직렬화 -> 메인 스레드 큐 -> ServerTransceiverManager -> EntityId별 ServerTransceiver -> 공통 메시지 처리 컴포넌트.
- 송신: 로컬 입력/ActionController -> 해당 엔티티의 ServerTransceiver -> NetworkClient의 공통 연결 -> 서버.
- 각 ServerTransceiver가 개별 소켓/수신 스레드를 만들지 않는다. 실제 연결, TCP 프레이밍 및 바이트 송수신은 NetworkClient가 담당한다.
- 컴포넌트가 붙어 있다는 사실이 이동/HP 결정 권한을 부여하지는 않는다. 엔티티 종류와 요청별 권한을 적용하며 서버도 세션 권한을 검증한다.
- 원격 플레이어와 몬스터의 서버 상태 수신이 다시 이동/피해 요청 송신을 유발하는 순환 경로를 만들지 않는다. 몬스터 이동/행동/HP의 서버 전담 원칙은 유지한다.
- 현재 예시 명칭이며 실제로 존재하지 않는 새 클래스를 이미 구현했다고 취급하지 않는다.

6. 작업 범위와 검수
- 구현 범위: 서버 구조, 캐릭터 State/Action, 이동/충돌/경계/영역, 접근, 공격, 피격/넉백/사망, 채집/제작 및 TXT의 수신/행동/표현 요소.
- 기존 자료구조와 코드를 우선 활용한다. 개념 변경이나 큰 수정은 해당 수정 전에 영향 범위를 보고한다.
- 최신 변경: 예비 씬을 종료하고 기존 LogIn/InGame 씬에서 새 구조와 기존 기능을 연결한다.
- 기존 캐릭터/레벨은 시각 자료로 사용하고 내장 AI/게임플레이 코드에 의존하지 않는다. 클립/이펙트/소켓은 표현 프로필로 연결한다.
- C++ 소유권은 unique_ptr/shared_ptr/weak_ptr를 수명에 맞게 사용하고 순환 참조를 피한다.
- Unity 편집은 사용자가 요청한 MCP를 우선한다. 연결 문제 또는 CLI가 필요한 작업은 사용자에게 설명하고 요청한다.
- 최신 변경: 기능마다 중간 검수를 기다리지 않고 사용자가 지정한 범위까지 진행한 후 코드/변경 파일/검증 결과를 보고한다.
- 2026-11-11 사용자 승인: 필요할 때 CLI 사용 허용. MCP에 필요한 도구가 노출되지 않으면 CLI로 같은 프로젝트 에디터를 제어한다.
- 새로운 개념이나 기술(BT 등)을 필요에 따라 임의 도입하지 않고 먼저 사용자에게 묻는다.
- 최신 변경: 이미 구현한 Action/State 기능은 유지하며 나머지 기존 기능(아이템/UI/퀘스트/튜토리얼/저장 등)을 이식 범위에 포함한다.

7. C++ 파일 구성 — 추가 지시
- 사용자 정정: 일반 클래스만 각각의 .h/.cpp로 분리한다. Enemy.h 등에 다른 일반 클래스의 정의가 섞여 있으면 분리한다.
- 구조체·패킷·열거형은 이 규칙에서 제외한다. 역할별 공용 헤더로 묶을 수 있고 데이터만 있는 타입에는 빈 .cpp를 만들지 않는다.
- 자기 자신의 전방 선언은 상호 참조 include 처리를 위해 자기 헤더에 둘 수 있다.
- 클래스 멤버 함수 본문은 대응 .cpp에 둔다. 템플릿 및 삭제 선언 등 C++ 언어상 헤더가 필요한 항목은 유지한다.
- .cpp에 지역/내부 클래스를 새로 정의하지 않는다.
- Visual Studio 프로젝트와 Header Files/Source Files 필터에도 파일을 함께 등록한다.
- 폴더 구성은 Visual Studio의 Header Files/Source Files 및 기능별 하위 폴더에 반영한다. 패킷을 개별 객체지향 클래스로 만들라는 의미가 아니다.
- 후속 사용자 지시: 동일 역할을 상수/열거형/구조체/별칭/처리 창구 등으로 과도하게 쪼개지 않는다. 관련 선언은 역할별 헤더로 통합하고, 별도 논리가 없는 호환 파일·중계 구현은 제거한다.
- 현재 통합 기준: Network/Packet.h(기존 패킷), Gameplay/Protocol.h(새 프로토콜·송신 별칭·직렬화), Gameplay/WorldTypes.h/.cpp(게임 데이터·기하 계산), Structs.h(기존 공용 데이터). EnemyState는 Enemy.h, IO 열거형/버퍼 상수는 IOContext.h에 둔다.

8. 원본 클라이언트 조작감 — 추가 지시
- 실제 InGame 씬에서도 기존 CameraMoving의 우클릭 회전·휠 줌·상대 위치/렌즈 설정을 유지한다.
- 기존 InputManager/Player의 Input.GetAxis, 카메라 기준 이동, 입력 크기와 회전 보간을 유지한다.
- 이동 속도는 기존 로그인에서 얻은 서버 스탯을 사용하고 서버 검증도 같은 값으로 적용한다.
- 마우스 클릭으로 상대를 선택하는 기능은 제거한다. 좌클릭 전투 진입과 E 타겟 순환은 기존 방식으로 적용한다.
- 채집은 기존 Space 입력으로 가까운 자원을 찾는다. 이미 시작된 공격의 대상은 선택 변경으로 바꾸지 않는다.

9. 기존 기능 전체 이식 — 2026-11-12 추가 지시
- 이미 작성된 캐릭터 모드/Action 상속/상태 전환과 이동 조작 개념은 유지한다.
- 기존 데이터 정의와 UI/이벤트/아이템 매개 개념을 재사용한다. 장착/해제, 소모품, 설치, 퀘스트 보상, 튜토리얼 진행, 저장은 서버가 확인하고 결과를 전달한다.
- 모델/레벨에 포함된 게임플레이 스크립트, AI, 애니메이션 이벤트를 새 실행 경로에서 사용하지 않는다.
- 자원 재등장은 클라이언트 타이머가 요청한다. 서버는 경과 시간, 고갈 상태, 재생성 세대 및 재등장 위치의 점유를 검사하고 잔량을 확정한다.
- 기존 구형 클라이언트의 위치/몬스터/스탯/인벤토리 변경 패킷으로 서버 검증을 우회하지 못하도록 차단한다.
- 원래의 DB 테이블을 사용하며 DB 스키마를 새로 도입하지 않는다. 맵별 몬스터 종류/수/생성 범위는 기존 MapInfo/Monster 조회 결과를 서버 시뮬레이션에 적용한다.
- 새 기술/설계 패턴을 임의로 추가하지 않는다. 이식 과정의 수명/패킷 순서/참조 정리 오류는 기존 구성 안에서 수정한다.

10. 서버 책임 분리 및 Validator — 후속 지시
- Core는 요청 흐름 조정, 요청 ID 중복 관리, ACK 결과 기록·반환을 담당한다. 게임 상태 로딩과 행동 처리, 검증 조건 및 체인 조립을 Core에 넣지 않는다.
- WorldState는 권위 있는 월드 데이터와 규칙 로딩을, GameplayProcessor는 상태 변경·행동 타이머·몬스터 갱신·완료 재확인을 담당한다.
- 검증 조건은 PacketValidator 또는 IngameValidator를 상속하는 구체 클래스로 만든다. 기존 LambdaValidator/ValidationGroup 순회 방식을 사용하지 않는다.
- PacketValidation 및 GameplayValidation의 초기화 함수에서 unique_ptr next로 체인을 연결하고, 멤버 변수에 보관하여 요청마다 재사용한다.
- 패킷 검증은 프레임/인증과 해석된 요청 계약을 검사하고, 인게임 검증은 공통 조건 후 요청별 체인을 실행한다.
- 중간 삽입 시 기존 next를 보존한다. 체인 구성 변경은 초기화 단계 또는 동일한 게임 처리 스레드에서 수행한다.
- 수신/해석/검증/처리/송신은 클래스로 분리하되, 이번 단계에서 OS 프로세스나 병렬 검증 워커를 추가하지 않는다. 검증 및 처리 사이의 상태 일관성을 유지한다.

11. Validator 상속 정정
- 공통 Validator가 next 연결, 실행 및 중간 삽입을 담당한다.
- PacketValidator는 직접 패킷 기본 검사를 구현하는 구체 클래스이며 별도 BasicPacketValidator를 두지 않는다.
- IngameValidator는 공통 Validator를 상속하는 추상 기반이고, 기능별 인게임 검증기는 이를 상속한다.

12. 서버 구성 및 초기화 — 2026-11-12 최신 지시 (이전 Core/WorldState 규칙 로딩 설명보다 우선)
- 최상위 ServerApplication이 DB/IOCP/인게임 구성요소를 묶어 소유하고 초기화·콜백 연결·시작·종료를 관리한다.
- 초기화 순서: IOCP 자원 준비 -> DB -> Game/Rule -> Map -> Monster/Level -> 외부 콜백 연결. 모든 단계 성공 후 Start에서 스레드와 접속 수락을 시작한다.
- 생성자에서 연결·파일 로딩·게임 스레드를 자동 시작하지 않는다. 실패 시 실행을 시작하지 않고 준비한 자원을 정리한다.
- ServerRuntime은 GameRules, WorldState, RefillSystem, ServerSteps를 소유한다. Core와 RequestDecoder는 사용하지 않는다.
- GameRules는 기준 데이터, WorldState/Map은 실행 상태, RefillSystem은 맵 상태를 참조하는 리필 처리다. 검증과 처리가 같은 리필 시스템을 참조한다.
- SessionManager는 연결만 관리하고 인게임 맵을 소유하지 않는다. 맵 실행 상태는 WorldState.maps 한 곳으로 통합한다.
- 단계 간 연결은 초기화 시 람다로 등록한다. 수신 측은 콜백을 호출하고 다음 단계가 자신의 처리 함수를 정의한다.
- 기존 게임 규칙·DB 스키마·패킷 형식과 클라이언트 리필 요청/서버 검증 방식은 유지한다.
- 자세한 클래스 소유·참조 관계는 서버초기화_소유관계_구현결과_2026-11-12.txt를 참조한다.
